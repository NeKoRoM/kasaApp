## 1. Загальний огляд та бізнес-домен

Екосистема **KasaApp** призначена для автоматизації роздрібної торгівлі (робоче місце касира / POS-термінал) з апаратною фіскалізацією на реєстраторах розрахункових операцій (РРО) лінійки **Exellio / Datecs** (DP-05, DP-150, FP-700 тощо), підтримкою торгових ваг по Bluetooth та централізованим керуванням мережею через FastAPI бекенд.

### Нормативні вимоги українського фіскального обліку:
1. **Диференційовані ставки ПДВ та Акциз:** Групи А (20%), Б (0%), В (7%), Г (звільнені), Д (не є об'єктом), окремий збір 5% роздрібного акцизу на тютюн/алкоголь.
2. **Кодування УКТЗЕД:** Обов'язкове зазначення 10-значного коду УКТЗЕД для всіх підакцизних товарів.
3. **Облік марок акцизного податку:** Введення серії та номера електронної або паперової акцизної марки при скануванні підакцизного товару (реалізовано в інтерфейсі чека `ReceiptProductList.kt` при `groupExcise == true`).
4. **Контроль фіскальної зміни:** Блокування каси після 24 годин без Z-звіту; обов'язкове зняття денного Z-звіту з обнуленням оперативної пам'яті.

## 4. Специфікація фіскального протоколу (Datecs / Exellio Protocol)

### 4.1. Фізичний та транспортний рівень
* **Профіль:** Bluetooth Classic SPP (Serial Port Profile).
* **Стандартний UUID:** `00001101-0000-1000-8000-00805F9B34FB`.
* **Кодування символів:** `Windows-1251` (CP1251) — обов'язкове для коректного відображення українських літер (І, Ї, Є, Ґ).
* **Розділювач полів:** Табуляція `\t` (`0x09`).
* **Кінець повідомлення:** `\r` (`0x0D`).
* **Таймаути зв'язку та сторожові таймери (Watchdog):**
  - Очікування квитанції команди (`ansJob`): 700–1000 мс $\rightarrow$ еміт `try_to_fix` (повтор або перехід до наступного коду).
  - Критичний таймаут зв'язку: 2000 мс $\rightarrow$ еміт `!!!!!` (скидання внутрішнього стану черги).
  - Дебаунс завершення пакетної транзакції: 300 мс тиші після останнього байта $\rightarrow$ `END_TRANSACTION`.

### 4.2. Формат кадру (`Protocol.kt`)
$$\text{Frame} = \langle 0x01 \rangle + \text{Len} + \text{Seq} + \text{Cmd} + \langle 0x05 \rangle + \text{BCC} + \langle 0x03 \rangle$$

1. **`0x01` (SOH):** Старт заголовка пакета.
2. **`Len` (4 байти):** Довжина пакета від `Len` до `ENQ` включно. Обчислюється як `byteArray.size + 5 + 30 + 3`, переводиться в hex, доповнюється нулями зліва до 4 розрядів і кодується за схемою Datecs Nibble Encoding.
3. **`Seq` (1 байт):** Порядковий номер пакета. Починається з `0x40` (64, ASCII '@'), інкрементується до `0x7C` (124, ASCII '|'), після чого скидається назад на `0x40`.
4. **`Cmd` (Текст команди + параметри через `\t`):** Корисне навантаження у кодуванні `Windows-1251`.
5. **`0x05` (ENQ):** Розділювач тіла кадру та контрольної суми.
6. **`BCC` (4 байти):** Контрольна сума — сума всіх беззнакових байтів від початку поля `Len` до `ENQ` включно. Значення переводиться в hex (4 розряди) і кодується через Datecs Nibble Encoding.
7. **`0x03` (ETX):** Байт завершення кадру.

> [!IMPORTANT]
> **Datecs Nibble Encoding (Кодування шістнадцяткових розрядів у Datecs/Exellio):**
> У протоколі Datecs значення кожного 4-бітного напівбайта (nibble 0..15) записується в кадр як символ із кодом `nibble + 0x30`:
> - Ніблі `0`..`9` перетворюються на звичайні ASCII символи `'0'`..`'9'` (`0x30`..`0x39`).
> - Ніблі `10`..`15` (`0xA`..`0xF`) перетворюються на ASCII символи наступні за дев'яткою:
>   - `10 (0xA)` -> `0x3A` (`':'`)
>   - `11 (0xB)` -> `0x3B` (`';'`)
>   - `12 (0xC)` -> `0x3C` (`'<'`)
>   - `13 (0xD)` -> `0x3D` (`'='`)
>   - `14 (0xE)` -> `0x3E` (`'>'`)
>   - `15 (0xF)` -> `0x3F` (`'?'`)
> Саме тому в кодах команд, полях довжини та контрольних сумах Datecs присутні символи `?`, `=`, `;`, `:`, `<`, `>`.

### 4.3. Алгоритми взаємодії з РРО

#### А. Циклічне вивантаження каталогу товарів (PLU Database Dump):
1. Відправка команди запиту останнього товару: `006;L\t100000\t` (або `kasaLast`).
2. Отримання відповіді з кодом товару `lastCode`.
3. Запит першого товару: `006;F\t1\t` (або `kasaFirstCode`).
4. Цикл зчитування:
   - Отримано товар $N$ $\rightarrow$ збереження в Room $\rightarrow$ запит `006;N\t` (або `kasaNext`).
   - Якщо отримано пошкоджений кадр $\rightarrow$ запит зі зміщенням `006;F\t${currentCode + 1}\t`.
   - Коли номер отриманого артикулу дорівнює `lastCode` $\rightarrow$ цикл завершено.

#### Б. Запис та верифікація товару (PLU Programming):
1. Відправка команди `006;P\t<17 полів>\t\u0005`.
2. Очікування підтвердження запису.
3. Запит перечитування товару за кодом для 100% верифікації: `006;R\t<codeId>\t`.

#### В. Налаштування фіскального кліше чека (Header Cliché):
1. Зчитування рядків кліше: послідовні запити `Header\t0\t\t` .. `Header\t7\t\t`.
2. Запис оновлених рядків: відправка `Header\t<index>\t<text>\t` з обов'язковою затримкою 100 мс між рядками.

#### Структура полів команди програмування товару (`006;P\t`):
1. `productId` — PLU/номер товару (1..100000)
2. `TAX` — Податкова група (`А`, `Б`, `В`, `Г`, `Д`, 1..8)
3. `section` — Номер відділу (1..99)
4. `group` — Товарна група (01..99)
5. `type` — Тип ціни (0 = вільна, 1 = фіксована)
6. `price` — Роздрібна ціна (наприклад `25.50`)
7. `salesAmount` — Накопичені продажі (`0.00`)
8. `remainder` — Поточний залишок товару
9. `barCode1` — Основний штрихкод (EAN-13)
10. `barCode2..4` — Додаткові штрих-коди (підтримка до 4 штрихкодів на 1 товар)
11. `name` — Найменування товару (до 52 символів у Windows-1251)
12. `weightOrUnit` / `productInSet` — Ознака товару (0 = штучний, 1 = ваговий, тощо)
13. `UKTZED` — 10-значний код УКТЗЕД для підакцизних товарів
14. `unitOfMeasurement` — Одиниця виміру (0 = шт, 1 = кг, 2 = м, 3 = л, 4 = г)

### 4.4. Байти статусу реєстратора (Status Bytes 0..5)
У відповіді на будь-яку команду Exellio повертає 6 байтів стану після розмежувача `\t`:

```
[Байти статусу Exellio / Datecs]
Байт 0 (Синтаксис & Помилки):
  • Bit 0: Помилка синтаксису команди
  • Bit 1: Неприпустимий код команди
  • Bit 2: Помилка часу / дати
  • Bit 4: Неприпустима команда для поточного стану каси
  • Bit 5: Помилка контрольної суми (BCC error)
Байт 1 (Папір & Принтер):
  • Bit 0: Закінчився контрольний папір
  • Bit 1: Закінчився чековий папір
  • Bit 2: Відкрита кришка принтера
  • Bit 4: Перегрів термоголівки
Байт 2 (Фіскальний стан):
  • Bit 0: Фіскалізовано (каса у фіскальному режимі)
  • Bit 1: Фіскальна пам'ять переповнена
  • Bit 3: 24 години зміни минули (потрібен обов'язковий Z-звіт!)
Байт 4 (Режим чека):
  • Bit 0: Відкрито нефіскальний чек
  • Bit 1: Відкрито фіскальний чек продажу
  • Bit 2: Дисплей покупця підключено
```

### 4.5. Протокол взаємодії з електронними вагами (Scales Protocol)
* **Транспорт:** Bluetooth Classic SPP (`00001101-0000-1000-8000-00805F9B34FB`).
* **Команда тарування (Tare):** `"T\r\n"` (`0x54 0x0D 0x0A`).
* **Формат потоку ваги:** Постійний потік текстових ASCII-повідомлень від вагового процесора (частота 5–10 Гц).
* **Парсинг ваги в клієнті:** Використовується регулярний вираз `Regex("-?\\d+\\.?\\d*")`, що коректно вилучає як позитивні, так і від'ємні значення маси (з плаваючою крапкою) для подальшого розрахунку суми вагового товару `price * weight`.
* **Таймаути асинхронного обміну (BluetoothController / ConnectThread):**
  - Очікування відповіді на команду (`ansJob`): 700 мс -> генерація маркера `NOT_ANSWER`.
  - Детекція завершення пакетної транзакції (`endComunication`): дебаунс тиші 300 мс після останнього байта -> генерація маркера `END_TRANSACTION`.

## 6. Кросплатформенний транспортний рівень (KasaTransport)

Для підтримки як мобільних (Android), так і настільних ОС (macOS, Windows):
```kotlin
interface KasaTransport {
    suspend fun connect(target: String)
    suspend fun write(data: ByteArray)
    suspend fun read(buffer: ByteArray): Int
    suspend fun disconnect()
}
```
1. **Android:** Реалізація через `BluetoothSocket` (RFCOMM SPP).
2. **Desktop (macOS / Windows):** Реалізація через віртуальний послідовний порт (Serial COM Port, оскільки Bluetooth SPP на ПК автоматично емулює `/dev/cu.DP05...` або `COMx`).

---

## 7. Архітектура серверної частини (FastAPI REST API)

### 7.1. Безпека та криптографія:
* **Асиметричне підписування:** **RS256** з парою ключів `jwt-private.pem` та `jwt-public.pem`.
* **Ролі користувачів:**
  - `SUPER_ADMIN_ROLE_ID = 100`
  - `ADMIN_ROLE_ID = 1`
  - `USER_ROLE_ID = 2` (Касир / Оператор)
* **Захист ендпоінтів:** Декоратор `require_roles([allowed_role_ids])`.

### 7.2. REST API Маршрути:
* `POST /jwt/login/` — видача JWT токена (`access_token`, `Bearer`).
* `GET/POST /products/` — отримання асортименту з фільтрацією за магазином та касою.
* `GET /products/search?q=...` — швидкий пошук товару за назвою або будь-яким із 4 штрих-кодів.
* `POST /Organization/stores/` — керування магазинами.
* `GET /users/`, `POST /user/` — керування персоналом торгових точок.
