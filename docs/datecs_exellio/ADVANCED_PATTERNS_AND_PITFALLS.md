## 1. Підводні камені таймаутів: Пастка 700 мс та байт `SYN (0x16)`

У ранніх версіях клієнтів (зокрема в legacy [`ConnectThread.kt`](file:///Users/neko/Documents/PlatformIO/Projects/kasaApp/repos/kasaApp3.0/bt/src/main/java/com/nekorom/bt/bluetooth/ConnectThread.kt#L46-L48)) для контролю відповіді каси використовувався фіксований таймер:
```kotlin
// НЕБЕЗПЕЧНИЙ ПАТЕРН:
ansJob = CoroutineScope(Dispatchers.IO).launch {
    delay(700)
    listeners.forEach { it.onReceive("NOT_ANSWER") }
}
```

### Чому цей патерн викликає критичні баги на касі:
1. **Тривалі операції:** Команди зняття Z-звіту (`0045Z`), запису у фіскальну пам'ять (`0048`), читання КСЕФ (`007D`) та масового програмування PLU (`006BP`) можуть тривати від 1.5 до 8 секунд (механічний друк + криптографічний підпис SAM-модуля).
2. **Службовий сигнал зайнятості `SYN (0x16)`:** Згідно з офіційною специфікацією Datecs v2.11 (розділ 3.3):
   > *«SYN 16H — цей код надсилається Slave при отриманні команди, яка потребує тривалого часу обробки. SYN надсилається кожні 60 мс доти, доки пакет відповіді не буде готовий до передачі».*
3. **Правильне рішення:**
   * Скинути таймаут при отриманні кожного байта `0x16`.
   * Загальний таймаут очікування першого байта — 1000 мс. Якщо надходить `0x16`, таймер продовжується ще на 500 мс на кожен `SYN`, або встановлюється глобальний захисний ліміт 15 секунд.

## 2. Детермінований парсинг кадру проти тайм-дебаунсу (300 мс)

У legacy-коді використовувався «дебаунс тиші»:
```kotlin
// НЕБЕЗПЕЧНИЙ ПАТЕРН:
endComunication = CoroutineScope(Dispatchers.IO).launch {
    delay(300)
    listeners.forEach { it.onReceive("END_TRANSACTION") }
}
```

### Проблеми підходу:
* Додає штучну затримку 300 мс на кожну операцію (чек з 15 товарів сповільнюється на 4.5 секунди!).
* При фрагментації Bluetooth-пакетів або завантаженні процесора планшета пауза може перевищити 300 мс в середині пакета, що призводить до розриву одного кадру на два пошкоджених шматки.

### Еталонний детермінований підхід (Frame Streaming FSM):
Протокол Datecs v2 має строгі межі:
$$\text{Початок} = \langle 0x01 \rangle, \quad \text{Розділювач} = \langle 0x05 \rangle, \quad \text{Кінець} = \langle 0x03 \rangle$$
1. Зчитувати байт `0x01` (SOH).
2. Зчитати рівно 4 нібли поля `LEN` $\rightarrow$ обчислити очікувану довжину тіла пакета.
3. Вичитати точно визначену кількість байтів до `0x05` (ENQ).
4. Зчитати 4 нібли `BCC` та термінатор `0x03` (ETX).
5. Миттєво перевірити контрольну суму $\rightarrow$ якщо сходиться, передати оброблений об'єкт `DatecsResponse` у ViewModel **без жодної мілісекунди затримки**.

## 3. Протокол «Krypton» (Криптон)

В Україні поруч із класичним протоколом Datecs v2 використовується протокол **Krypton** (наприклад, у популярних фіскальних реєстраторах **Datecs FP-3530T**, **FP-320**, **FP-101 Smart**, **FP-T88**).

### Основні відмінності Krypton від Datecs v2:
| Параметр | Datecs v2 (серія X: DP-25X, FP-700X) | Krypton (FP-3530T, FP-320, FP-101) |
| :--- | :--- | :--- |
| **Архітектурний стандарт** | Фірмовий протокол Datecs | Орієнтований на міжнародний стандарт **OPOS / UnifiedPOS** |
| **Коди команд** | 4-байтний нібл-ASCII (`0030`, `0031`) | Двійкові 1-2 байтні шістнадцяткові коди (`0x040A`, `0x02`, `0x10`) |
| **Перевірка стану** | 8 статусних байтів (0x80..0xFF) | 6 або 8 байтів OPOS-статусу |
| **Діагностичні утиліти** | `FPWinXIP`, `UkrPshLocalN` | `FPWinX`, драйвери ArtSoft |
| **Блокування артикулів** | Заборона зміни PLU під час відкритої зміни повертає код `-111004` | Помилка `0x040A` (Артикул з даним кодом заблокований у відкритій зміні) |

## 4. Облік підакцизних товарів, кодів УКТЗЕД та акцизних марок

Згідно із Законом України № 265/95-ВР та наказами Мінфіну, українські РРО Exellio вимагають обов'язкового передавання додаткових реквізитів для підакцизних товарів:

1. **Код УКТЗЕД (10 цифр):**
   * Передається перед назвою товару або як окремий атрибут у команді `49 (0x31)`.
   * Формат у назві: `УКТЗЕД 2208601100 Горілка Преміум 0.5л`.
2. **Марка акцизного податку (паперова або електронна з Дії):**
   * Серія та номер акцизної марки (наприклад, `АААА123456`).
   * Якщо товар запрограмовано з ознакою акцизу, але касир не передав марку — реєстратор повертає помилку **`-111096` (`ERR_R_EXCISE_PLU_WITHOUT_EXCISE_STAMP`)**.
   * Якщо марка має невірний контрольний розряд або повторюється — апарат повертає **`-111097` (`ERR_R_EXCISE_PLU_FORBIDDEN`)**.

## 5. Пінпад банківського терміналу через РРО (Pinpad Bridge)

Унікальна функція пристроїв Datecs/Exellio полягає в тому, що банківський POS-термінал (Ingenico, Verifone, PAX) можна підключити безпосередньо до COM-порту каси (`PinpadComPort = COM1/COM2`):

```mermaid
flowchart LR
    Host["POS-додаток (kasaApp)"] -->|Bluetooth / TCP| ECR["РРО Datecs / Exellio"]
    ECR -->|RS-232 Port 2| Pinpad["Банківський термінал"]
```

1. **Оплата карткою (Команда 53, опція 2 або 12):**
   * Запит: `53\t12\t45.00\t1\t`
   * РРО самостійно надсилає суму в термінал.
   * Клієнт прикладає картку та вводить PIN.
   * Термінал відповідає реєстратору, а реєстратор одразу друкує чек і повертає хосту банківські реквізити транзакції:
     `{ErrorCode}\tD\t0.00\t{AuthCode}\t{CardType}\t{MaskedPAN}\t{MID}\t{RRN}\t{TID}\t{Amount}\t{Date}\t{Time}\t`
2. **Перевага:** POS-додатку не потрібно реалізовувати окремі протоколи BPOS / Posnet / CECR для кожного банку — РРО бере всю роботу на себе!

## 6. Тестування без фізичного заліза через емулятор KasaApp

У нашому репозиторії вже реалізовано повноцінний емулятор Datecs:
* `datecs_framer_logic.py`, `datecs_engine_logic.py`, `datecs_socket_transport.py`.

### Як тестувати Android-застосунок з емулятором:
1. Запустити локальний бекенд/емулятор:
   ```bash
   ./run_backend.sh
   ```
   Емулятор запускає TCP-сервер Datecs на порті `4999`.
2. Прокинути порт на підключений Android-планшет або емулятор:
   ```bash
   adb reverse tcp:4999 tcp:4999
   ```
3. У налаштуваннях `kasaApp-v5` вибрати з'єднання по мережі на адресу `127.0.0.1:4999`. Додаток надсилатиме реальні байти Datecs v2, а емулятор відповідатиме валідними статусними байтами та розрахунком BCC!
